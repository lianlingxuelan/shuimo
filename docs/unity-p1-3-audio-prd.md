## 0. TL;DR（给架构师的四句话）

1. **本期不是"从零做音频系统"，是"把已经挖好的两个坑埋上线"。** 内核里 `PlaySfx` 已在 12 个位置被调用、key 已写死，但全仓**零 `PlaySfx =` 赋值**。本质工作量在 Unity 侧。
2. **零音频二进制资源是 P0 红线**，与 `SpriteFactory` 的"一张 png 都没有"完全对称：音效必须 `AudioClip.Create` + 逐样本合成。这条不可谈判。
3. **⚠️ 三处任务简报与代码实际不符，以本文档为准**，见 §1.3。最要命的是**技能 id 的真实字符串**——照简报写会导致 3/4 的技能音效永远匹配不上。
4. **BGM 的结论是：本期不做旋律 BGM，改做"环境衬底"（P1），旋律 BGM 降 P2 且需主创拍板破例。** 理由不是偷懒，是"零二进制资源"这条红线与"有旋律的配乐"在本质上冲突。完整论证见 §5，这是本 PRD 唯一一个需要上级决策的产品取舍。

## 1. 现状与事实基线

### 1.1 内核已经把话说完了，只是没人听

全仓 `AudioSource` / `AudioClip` / `AudioSettings` 命中数 = **0**（唯二命中是 `CombatEventsUnity.cs:10` 的一句注释，和 `WorldBuilder.cs:652` 的一个 `AudioListener`，见 §1.4）。

但**两个音效出口早就存在**，且都已在事件里被调用：

| 出口 | 文件:行 | 委托签名 | 赋值方 |
|---|---|---|---|
| 出口 ① | `Assets/Scripts/Systems/Combat/Unity/CombatEventsUnity.cs:46` | `Action<string> PlaySfx` | **无（零订阅）** |
| 出口 ② | `Assets/_Project/Scripts/Runtime/CombatEventsT3Unity.cs:42` | `Action<string> PlaySfx` | **无（零订阅）** |

两者都写了 `if (PlaySfx != null)` 判空保护，即"空即原路径"——**没接音频时安静跳过，不报错**。这个既有约定必须在本期继续成立（见 R-07）。

### 1.2 P1-2 只做完了打击感的一半

P1-2 已交付顿帧 / 屏震 / 分阵营闪白 / 伤害飘字四件套（`HitFeedbackDirector`、`HitFeedbackConfig`、`DamagePopupLayer`、`CameraShake`）。也就是说：

> **现在玩家挨打时，屏幕会震、角色会闪红、数字会跳出来——但整个过程是全程静音的。**

视觉侧的分档语言（轻击/重击、玩家/敌人）已经建立，本期的听觉侧应当**沿用同一套分档口径**，而不是另起一套（见 R-04 的强弱分档）。

### 1.3 ⚠️ 三处任务简报与代码实际不符（以本文档为准）

我在动笔前逐条核对了简报里的现状描述，发现三处偏差。第一处是硬伤：

**① 技能 id 的真实字符串不是简报写的那四个**

简报写"已注册的技能：`basic` / `circle_burst` / `blood_lotus` / `dodge_roll`"。代码实际（`Assets/Scripts/Systems/Combat/Skills/SkillConfig.cs:174-183`）：

| 简报写的 | **代码实际常量值** | 常量名 |
|---|---|---|
| `basic` | **`skill_basic_slash`** | `SKILL_BASIC_SLASH` |
| `circle_burst` | **`skill_circle_burst`** | `SKILL_CIRCLE_BURST` |
| `blood_lotus` | **`skill_blood_lotus`** | `SKILL_BLOOD_LOTUS` |
| `dodge_roll` | `dodge_roll` ✅ | `SKILL_DODGE_ROLL` |

出口 ② 在 `:127` 传的是 `def.Id`，也就是**上表右列的完整字符串**。按简报的短名去建映射表，四个技能音效会哑掉三个，而且因为"未知 key 静默降级"是本 PRD 的 P0 要求（R-07），**这个错误不会报错、不会崩，只会安静地没有声音**——属于最难排查的一类 bug。§4.1 的清单已按实际值给出。

**② 闪避不会双触发（简报未提，但这是个自然的担心）**

出口 ② 有两处 `PlaySfx`：`:127`（`OnSkillCast` 传 `def.Id`）和 `:181`（`OnDodgeStart` 传 `SKILL_DODGE_ROLL`）。看起来闪避可能既走 cast 又走 dodge、响两声。

**实际不会。** 内核 `Encounter.cs:753-760` 是严格的 `if/else`：

```
if (def.Action == ActionKind.Dodge)  → evt.OnDodgeStart(...)
else                                  → evt.OnSkillCast(...)
```

所以 `dodge_roll` 只从 `:181` 出来一次。**本期不需要为闪避做跨链路去重**——这一点值得写明，因为 P1-2 恰好踩过对称的坑（`CombatEventsT3Unity.cs:146` 那段注释记录了 `PlayHitFlash()` 被两条链路重复触发的事故）。

**③ "8 个内核 key" 的实际调用点是 6 处、产出 8 个 key**

简报的表格列了 8 行，但其中 `sfx_player_hurt`/`sfx_enemy_hit` 同出 `:124` 的三元表达式，`sfx_enemy_death`/`sfx_boss_death` 同出 `:143`。即 **6 个调用点产出 8 个可能的 key**。不影响清单内容，但影响接线时的验证方式：只需验证 6 个事件路径，不是 8 个。

### 1.4 一个会让"全部功能都对但就是没声音"的隐患

`WorldBuilder.cs:641` 的 `SetupCamera()` 里，`AudioListener` **只在兜底分支被添加**：

```
Camera cam = Camera.main;
if (cam == null) {            // ← 只有"场景里相机被删了"才走这里
    ...
    go.AddComponent<AudioListener>();   // :652
}
```

正常路径（场景自带 Main Camera）**完全不检查 `AudioListener` 是否存在**。Unity 新建场景的默认相机确实自带 `AudioListener`，所以大概率没事——但这是"靠场景文件的运气"，不是靠代码保证。而且本工程的 `Clean And Rebuild` 流程会反复增删场景对象，风险是真实的。

更麻烦的反向情况：如果场景里**同时存在两个** `AudioListener`，Unity 会持续刷警告且音频行为不确定。

→ 因此 R-08 把"保证有且仅有一个 `AudioListener`"定为 **P0**。这不是防御性编程洁癖，这是"用户 Play 之后一点声音都没有，然后来问是不是功能没做"的直接预防。

## 2. 产品目标

### 2.1 一句话说清"为什么现在必须补声音"

**因为现在这款游戏，把耳机摘了和戴上完全一样。**

P1-2 之后，一次命中会顿帧、会震屏、会闪红、会跳数字——**唯独不会响**。打击感是一个视听联觉的整体，视觉那一半做得越好，听觉的缺席就越刺耳（字面意义上的）。具体缺三样：

- **打击不"实"**：剑刃切入身体这件事，视觉上有了，听觉上没有。人耳对瞬态（transient）的敏感度高于人眼对闪烁的敏感度，**没有"咔"的那一声，顿帧就只是画面卡了一下**。
- **危险不"响"**：BOSS 阶段切换、召唤、冲击波是三个"你该躲了"的强预警事件。现在它们只有视觉表现，玩家在专注走位时**很容易完全错过**。声音是唯一不需要盯着看的通知信道。
- **世界不"活"**：静音的战斗场景像一张会动的截图。这一点不需要旋律 BGM 就能解决（见 §5）。

### 2.2 三个正交目标

| # | 目标 | 达成判据 |
|---|---|---|
| G-1 | **让每一次战斗事件都有听觉回应**，且强弱与视觉分档一致 | §4.1 清单里 12 个 key 全部有声，且轻击/重击可听辨（A-1 ~ A-4） |
| G-2 | **不引入任何音频二进制资源**，clone 即可跑 | 仓库内 `.wav`/`.ogg`/`.mp3` 计数为 0（B-1） |
| G-3 | **音频永远不能让战斗出问题**——不崩、不卡、不改数值 | 倍率指纹 `2.5294x` 不漂移，且拔掉音频设备照常通关（B-2 ~ B-5） |

### 2.3 这一版刻意不做什么

见 §6。一句话：**只做"听得见事件"，不做"听得见音乐"。**

### 4.3 音色调色板（保持水墨仙侠调性）

这是一条统领全表的约束：**所有音效应当听起来像"木、石、水、布、丝弦、金石"，而不是"电子合成器、科幻能量、赛博音效"。**

程序化合成天然容易滑向后者（正弦扫频听起来就很"科幻"）。规避手段：

- **优先用噪声 + 滤波塑形**，而不是纯振荡器音色；
- **必须加瞬态**（前 5~15 ms 的高频冲击），这是"物理撞击"与"电子音"的分界；
- **避免长时间的纯音持续**，纯正弦拖长立刻变科幻；
- **金石类音色**（钟、磬）可用少量非谐波泛音叠加，这是最贴合仙侠调性的一类，建议用在 BOSS 相关事件上。

> 与 P1-2 §7 Q4 的调性争议同源：水墨的美学核心是**克制**。音效同理——**宁可偏轻，不可偏吵**。所有音量建议值若有疑虑，一律往小了取。

## 5. BGM：本期的核心产品取舍

> 简报要求我在这里给出明确判断而不是含糊其辞。以下是我的结论和完整论证。

### 5.1 结论

| 项 | 判断 |
|---|---|
| **本期做不做旋律 BGM？** | **不做。** 降为 P2（`bgm_main`），且**需主创拍板是否为它破"零二进制资源"的例**。 |
| **那战斗场景就静着？** | **不。** P1 做 `amb_wind_loop` **环境衬底**——这是一个不同的、程序化能做好的东西。 |
| **这个决定可以被推翻吗？** | 可以，但推翻的前提是主创同意引入一个音频二进制文件，或者同意投入专门的作曲工作量。**不能靠"再努力合成一下"绕过去。** |

### 5.2 为什么音效可以程序化，BGM 不可以

这两件事看起来都是"用 `AudioClip.Create` 填样本"，但难度不在一个量级上。区别在于**人耳对两者的评判标准完全不同**：

**音效是抽象的，BGM 是具体的。**

- 玩家听到一声"噗"，不会去想"这声音像不像真的刀砍进肉里"，只会判断"有没有反馈、够不够干脆"。**没有人知道剑气打中妖物应该是什么声音**，所以合成音只要瞬态够硬、包络合理，就是可信的。程序化在这里胜率极高。
- 而音乐一响，每个玩家都是专家。旋律好不好听、和声顺不顺、节奏稳不稳——这是**人类共有的、极其苛刻的审美判断**。一段"技术上正确"但没有作曲意图的音乐，听感上比静音更糟：它会让人立刻觉得"这游戏很廉价"。

### 5.3 逐条拆解"程序化 BGM"的现实性

我把它拆成四个子问题，诚实地评估每一个：

| 子问题 | 现实性 | 说明 |
|---|---|---|
| **音色能做吗？** | ✅ **能，而且不难** | 古琴/琵琶这类拨弦音色用 Karplus-Strong 算法（一个延迟线 + 低通反馈）就能做出相当可信的效果，代码量约 20 行。箫/笛可用滤波噪声 + 共振峰近似。**这一关不是瓶颈。** |
| **节奏/结构能做吗？** | ✅ **能** | 音符表 + 包络调度，纯工程问题。 |
| **旋律能做吗？** | ❌ **这是真正的墙** | 两条路都走不通：<br>**(a) 算法生成旋律**（马尔可夫链 / 规则约束）——产出的是"没有意图的音符序列"，听起来像屏保音乐，60 秒内必然暴露。<br>**(b) 硬编码音符数组**——技术上完全可行，但这本质上是**"让人在 C# 数组里作曲"**。工作量不是编程工作量，是作曲工作量，而且我们团队里没有作曲。 |
| **内存/性能扛得住吗？** | ⚠️ **要设计，但可控** | 一段 90 秒立体声 44.1 kHz 的 float 数据 ≈ **31.7 MB**（44100 × 90 × 2 × 4 B），对一个连 png 都没有的工程来说是突兀的一大块。<br>缓解：单声道 + 22050 Hz 采样率，12 秒素材 ≈ **1.06 MB**，完全可接受。这也正是"短循环衬底"方案在内存上远优于"长旋律 BGM"的原因。 |

**结论落在第三行**：不是做不出声音，是做不出**值得听的旋律**。而"零外部音频二进制资源"这条红线，恰恰就是把"引入一段人类作曲家写的音乐"这条路堵死的那条线。

**这两者在本质上冲突，必须有人做选择，而不是由我在 PRD 里假装它不存在。**

### 5.4 那么本期做什么：环境衬底（Ambience）

**环境衬底不是简化版 BGM，它是另一个品类。** 它的评判标准回到了"音效"那一侧——抽象、无旋律、不接受审美审判：

| 特性 | 说明 |
|---|---|
| **是什么** | 8~16 秒可无缝循环的低频风声 / 空山回响，音量极低（默认 BGM 通道 0.5 × 主音量 0.8 ≈ 0.4） |
| **怎么合成** | 滤波噪声（低通 400~800 Hz）+ 两三个缓慢 LFO（0.05~0.15 Hz）分别调制音量、滤波截止和声像。**无旋律、无节拍、无调性** |
| **无缝循环怎么保证** | 所有 LFO 周期必须能整除循环总时长，且首尾样本做交叉淡化（crossfade ≈ 200 ms）。**这是本项的唯一技术难点，必须验收**（A-9） |
| **为什么它解决问题** | US-7 的诉求是"世界是活的"，不是"我想听音乐"。**死寂感由环境音解决，不由旋律解决。** |
| **为什么它符合调性** | 水墨的美学核心是**留白**。一张水墨画不需要配乐，它需要的是风声。**克制的环境音比一段平庸的旋律更贴合本作调性**——这不是退而求其次的借口，我认为它在艺术上就是更对的选择。 |

### 5.5 给主创的决策建议

如果将来要做旋律 BGM，我建议的优先顺序是：

1. **首选：为 BGM 单独破例，引入 1 个 `.ogg` 文件**（约 2~4 MB）。红线的本意是"clone 下来直接能跑，不用问资源在哪个网盘"——**一个进版本库的 ogg 完全满足这个本意**，它并不违背红线的精神，只违背字面。这是成本最低、效果最好的路。
2. **次选：硬编码音符表 + Karplus-Strong 合成**，但**必须先找到愿意写这段旋律的人**。没有作曲，不要开工。
3. **不建议：算法生成旋律。** 投入产出比最差，且结果不可控。

> 优先级口径：**P0 = 缺了不能交付；P1 = 应该有，缺了体验打折；P2 = 有余力再做。**

### 6.1 P0（9 条，必须有）

#### R-01　双出口接线与对称拆线

- 在 Unity 侧（`Assets/_Project/Scripts/Runtime/`）实现音频总控，并把它接到**两个** `PlaySfx` 出口上：
  - `CombatEventsUnity.PlaySfx`（`CombatEventsUnity.cs:46`）
  - `CombatEventsT3Unity.PlaySfx`（`CombatEventsT3Unity.cs:42`）
- 接线位置应与 P1-2 的 `SetupHitFeedback()` / `TeardownHitFeedback()` 对称（`CombatBridge.cs:500` / `:561`）：**每一次 `+=`/赋值都必须有严格一一对应的解除**。P1-2 的注释里已经把这条房规写死了，本期照办。
- **不得**在内核脚本根 `Assets/Scripts/` 下新增任何音频实现代码。对既有文件的改动应为**零**（本期理论上不需要改内核任何一行，见 §7 Q1）。

#### R-02　`AudioConfig` 常量表

- 所有可调数字（音量默认值、各 key 的时长/增益/节流窗口、voice 上限、采样率等）集中在**一张 `static class AudioConfig` 常量表**里，位于 `Assets/_Project/Scripts/Runtime/`。
- 理由与 `HitFeedbackConfig.cs` 完全相同，不再重复论证：**调音是跨十几个音效一起调的，参数必须摆在同一屏里。**
- **明确不要 ScriptableObject 配置资产**——会引入 `.asset` 二进制，破坏 §7.1 红线，且 grep 不到。

#### R-03　程序化音频合成器（零二进制）

- 所有 `AudioClip` 必须通过 `AudioClip.Create` + 逐样本填充生成，**工程内不得出现任何 `.wav` / `.ogg` / `.mp3` / `.aiff` / `.asset` 音频资源**。
- 参照 `SpriteFactory.cs` 的既有范式：
  - **懒生成 + 字典缓存**（`SpriteFactory.cs:33` 的 `Dictionary<string, Texture2D>`），同一 key 只合成一次；
  - **⚠️ 必须提供对称的 `Clear()`**（`SpriteFactory.cs:48`）。`AudioClip` 与 `Texture2D` 同为**非托管资源，GC 不会回收**，世界每次 `Clean And Rebuild` 都 new 一批而不释放，就是稳定泄漏。这一条**不是可选项**。
- **合成时机**：所有 P0 音效应在战斗开始前（Bootstrap / WorldBuilder 阶段）**预合成完毕**，不允许在第一次命中时才现场合成——那会造成第一次命中掉帧。
- 建议采样率 **22050 Hz 单声道**（短音效听感差异极小，内存减半，见 §7 Q4）。

#### R-04　核心 12 个 key 全覆盖

- §4.1 表中 12 个 key **全部必须有声**，且 key 字符串与 `SkillConfig.cs:174-183` / `CombatEventsUnity.cs` 的实际值**逐字符一致**（重申 §1.3 ①）。
- 强弱分档**沿用 P1-2 的口径**，不另起一套：玩家侧受击音应明显重于敌人侧（与朱砂红闪白 / 更强屏震对应）。
- 若内核未来新增技能，其 `def.Id` 会自动成为新 key。**未注册的 key 必须走静默降级（R-07），不得抛异常。**

#### R-05　voice 管理与高频合流

> 这是本期最容易做砸的一条。围攻场景下每秒十几次命中，天真实现会直接糊成一堵噪音墙。

**产品层面的期望行为：围攻时应该听起来像"密集的雨点"，而不是"持续的白噪音爆音"。宁可少响一次，不可糊成一片。**

四层保护，建议全部实现：

| 层 | 规则 | 建议值 |
|---|---|---|
| **① 同 key 节流** | 同一 key 在窗口内重复触发直接丢弃 | 高频类（`sfx_enemy_hit` / `skill_basic_slash` / `dodge_roll`）**50 ms**；低频类（死亡 / BOSS 三件套）**不节流** |
| **② 同 key 并发上限** | 同一 key 同时发声的 voice 数 | **≤ 3** |
| **③ 全局并发上限** | 所有音效同时发声的 voice 总数 | **≤ 16**，超出时抢占**最旧**的一个 |
| **④ 连触递减增益** | 同 key 连续触发时逐次衰减音量，避免叠加爆音 | 第 n 次增益 × `0.7^(n-1)`，**下限 0.4**；该 key 静默 **200 ms** 后计数复位 |

- **`sfx_boss_death` 与 `sfx_boss_shockwave` 豁免抢占**：这两个是情绪/预警关键音，不允许被杂兵的命中音挤掉。
- 实现方式（`AudioSource` 池 vs `PlayOneShot`）由架构师定，产品侧只钉死上述可听辨的行为。

#### R-06　音量分层与主静音

| 通道 | 默认值 | 说明 |
|---|---|---|
| **Master（主音量）** | **0.80** | 不取 1.0：合成音的瞬态偏硬，留 20% 余量避免削波 |
| **SFX** | **0.90** | 本期的主角 |
| **BGM / Ambience** | **0.50** | 衬底必须明显低于音效，它的作用是垫底不是抢戏 |

- 最终增益 = `Master × 通道音量 × 单音效增益（表内定义）`，全部取值域 `[0, 1]`，结果需 clamp。
- **主静音开关**：一个布尔总开关，置位后**跳过 `Play` 调用本身**（不是把音量设成 0），省 voice 也省 CPU。
- 建议绑定 **`M` 键**切换静音——**需架构师确认与现有输入映射无冲突**（见 §8 Q5）。
- 音量为 0 的通道同样应跳过 `Play`。

#### R-07　全链路静音安全降级

> **静音是安全的降级路径，不是错误。** 这条是 §7.4 红线的需求化。

必须静默降级（**打印至多一次 warning，绝不抛异常、绝不中断战斗**）的情形：

| 情形 | 期望行为 |
|---|---|
| 未知 / 未注册的 key | 跳过，**该 key 只警告一次**（参照 `SpriteFactory.cs:35` 的"已警告集合"范式——缺失资源会在每帧反复命中失败分支，必须去重） |
| `AudioClip.Create` 返回 null 或抛异常 | 该 key 永久标记不可用，后续调用直接跳过 |
| 无音频设备 / 设备被拔出 | 战斗完全照常，不崩不卡 |
| `AudioListener` 缺失 | 见 R-08 |
| voice 池耗尽 | 按 R-05 ③ 抢占，不排队、不阻塞 |
| 玩家已静音 | 跳过 `Play` |

- **整条 `PlaySfx` 链路必须被异常隔离**：任何音频异常都不得冒泡到战斗事件调用栈。内核在 `OnHit` 里调 `PlaySfx`，一个音频异常把整场战斗掀了是绝对不可接受的。
- 沿用既有的"空即原路径"约定（`CombatEventsT3Unity.cs:124` 注释）：**缺失的能力只是不发生，绝不让整条链路崩掉。**

#### R-08　`AudioListener` 保障（有且仅有一个）

- 音频系统初始化时**必须自检**：场景中 `AudioListener` 数量为 0 则补建一个（挂在主相机上），数量 > 1 则保留主相机上的、禁用其余并打印一次 warning。
- 理由见 §1.4：`WorldBuilder.cs:652` 只在"相机被删了"的兜底分支加 `AudioListener`，正常路径完全不保证。**这是"所有代码都对但一点声音都没有"的头号嫌疑。**

#### R-09　暂停 / 终局 / 重开的音频收敛

- 复用既有的唯一闸门 `CombatBridge.IsGameplayBlocked`（`= IsRunOver || _menuPaused`，`CombatBridge.cs:159`）。**不得新增第二个音频专用暂停标志。**
- 具体行为：

| 状态 | 期望行为 |
|---|---|
| 菜单暂停（`SetMenuPaused(true)`） | **不新起**任何战斗音效；已在播的短音效**允许自然放完**（都 < 1 s，强行切断反而突兀）；环境衬底**压低到 30%**（duck），**不完全停**——完全静音会造成明显的听觉断裂 |
| 恢复 | 环境衬底在 ≈ 300 ms 内平滑回到原音量，**不得瞬间跳变** |
| RunOver / 死亡结算 | 停止所有战斗音效；环境衬底 duck 到 30% |
| 重开 / 返回主菜单 | **所有正在播放的 voice 必须被清理干净**，不允许上一局的声音漏到新一局或主菜单里 |

- ⚠️ **不得使用 `Time.timeScale` 来"暂停"音频**。`PauseMenuHud.cs:12` 的注释已明确记录本工程为何不用 timeScale，且 P1-2 §6.1 已将其列为一票否决项。本期继续遵守。

## 7. 硬约束（产品级，不可谈判）

### 7.1 零外部音频二进制资源

- 工程内**不得新增任何** `.wav` / `.ogg` / `.mp3` / `.aiff` / 音频 `.asset`。所有声音一律 `AudioClip.Create` + 逐样本程序化合成。
- 这与 `SpriteFactory.cs` 的既有实践严格对称——该文件头注释写着"**工程里因此一张 png 都没有**"，所有可见物（地块、角色方块、剑气月牙、血条）都是 `Texture2D` 逐像素画出来的。**声音应当享受同等待遇。**
- 红线的本意：**clone 下来直接能跑，不会有人问"资源在哪个网盘"。**
- 唯一可能的例外是 R-16 旋律 BGM，且**必须经主创显式批准**（§5.5）。在批准之前，例外不存在。

### 7.2 内核绝不能出现 `AudioSource`

- `Assets/Scripts/` 下**永远不得出现** `AudioSource` / `AudioClip` / `AudioListener` / 任何音频播放调用。
- 理由已由内核自己写在注释里（`CombatEventsUnity.cs:9-11`）：

  > 内核必须能在没有引擎的情况下跑完一整场战斗（这是 t1_selfcheck.py 的前提）。
  > 只要内核里出现一句 AudioSource.Play()，对拍就再也跑不起来了。

- 分工边界：**内核只抛事件说"发生了什么"，Unity 侧决定"听起来是什么样"。** 本期所有实现代码应落在 `Assets/_Project/Scripts/Runtime/`（asmdef = `Xianxia.Unity.T2`）。

### 7.3 音效不得反过来影响战斗数值

- **确定性指纹：围攻/单挑伤害倍率 `2.5294x` 必须一位不差。**
- 音频系统只能**读取**战斗事件，**不能写回**任何内核状态。
- ⚠️ **特别提醒 R-12（音高随机化）**：这是本期唯一一处会引入随机数的需求，也是唯一一处有可能污染确定性的地方。**必须使用表现层自己的 `System.Random` 或 Unity `Random`，严禁复用内核的 `SkillRng` / `PCG32` 流**（`SkillConfig.cs:156-167`）——从内核随机流里多抽一个数，后续所有战斗随机就全部错位，指纹当场漂移。
- **同一段输入序列，开音频和关音频跑出来的战斗结果必须逐位一致。**
- 禁止 `Time.timeScale`（继承 P1-2 §6.1）。

### 7.4 静音必须是安全的降级路径，不是错误

- 没有音频设备、玩家关掉了声音、`AudioClip` 合成失败、`AudioListener` 缺失、key 未注册——**这些都不该让战斗崩，也不该刷屏报错。**
- 需求化为 R-07，验收见 §8.3。

## 8. 待确认问题

> Q1 影响实现结构，Q2 需要主创拍板，建议优先解决。

**Q1（结构，需架构师确认）：两个出口的 key 命名空间不一致，要不要统一？**

出口 ① 传 `sfx_player_hurt` 这类**带 `sfx_` 前缀的字面量**；出口 ② 传 `def.Id`，也就是 `skill_basic_slash` / `dodge_roll` 这类**裸技能 id，没有前缀**。

三个选项：

- **(a) 不改任何代码，音频侧同时接受两套命名**（**我倾向这个**）。理由：`def.Id` 是数据驱动的——将来新增技能，音效 key 自动就有了，不需要改内核。若强行要求 `sfx_` 前缀，每加一个技能都得回内核加一行映射，是负担。
- **(b) 改 `CombatEventsT3Unity.cs:127` 为 `PlaySfx("sfx_" + def.Id)`**。该文件在 Unity 层（`Assets/_Project/`），改它不碰内核，成本很低。好处是 key 命名统一、日志好读。
- **(c) 改内核出口 ①**。**直接否决**，无收益且碰内核。

我按 (a) 写的 PRD。若架构师认为 (b) 更干净，我没有意见——**但需要在开工前定，因为它决定映射表的 key 集合。**

**Q2（产品，需主创拍板）：旋律 BGM 要不要为它破"零二进制资源"的例？**

这是本 PRD 唯一一个我无权决定的问题。完整论证见 §5，我的建议见 §5.5（首选引入 1 个 ogg）。**在拍板之前，R-16 不开工，本期只做 R-10 环境衬底。**

**Q3（体验）：环境衬底在主菜单要不要播？**

我倾向**要**——主菜单完全静音的第一印象很差，而环境衬底正好能在玩家还没进战斗时就建立氛围。但这需要音频系统的生命周期**早于** `CombatBridge`（主菜单阶段战斗还没装配）。请架构师评估初始化时序，若成本高则本期只在战斗场景播。

**Q4（技术，需架构师确认）：22050 Hz 单声道够不够？**

R-03 建议 22050 Hz 单声道，内存减半。风险是高频瞬态（`sfx_poise_break` 的"咔"、`skill_basic_slash` 的破空）在 22050 Hz 下奈奎斯特频率只有 11 kHz，**可能听起来发闷**。若实测发闷，建议**只把高频类音效提到 44100 Hz**，其余保持 22050 Hz，而不是全局提高。

**Q5（输入）：静音快捷键用 `M` 键会不会冲突？**

R-06 建议 `M`。本工程输入映射在 `Assets/_Project/Scripts/Runtime/Input/` 下，我没有逐一核对全部绑定。**请架构师确认 `M` 未被占用**；若冲突，任选一个未占用键，产品侧无偏好。

**Q6（性能）：预合成 12 个音效会让启动卡多久？**

R-03 要求战斗开始前预合成完毕。12 个音效总时长约 5 秒音频，22050 Hz 单声道约 11 万样本/秒 → 总计约 55 万次样本运算，**理论上是毫秒级**。但我无法实测（本环境无 Unity）。如果实测启动有可感知卡顿，请反馈，我把非 P0 音效改成懒合成。

**Q7（听感，需现场调）：`skill_basic_slash` 和 `sfx_enemy_hit` 会不会打架？**

一次成功普攻会先后响两声（挥击 + 命中），间隔取决于技能帧数。如果间隔太短（< 60 ms），两声会糊成一声，听起来像单纯的音量变大而不是两个事件。**这个只能在本地实听后调**——若糊了，建议把 `skill_basic_slash` 再压薄一档（缩短到 80~100 ms 并降低增益）。

## 9. 验收标准

> 口径：**用户在本地 Unity 打开工程、点 Play、戴上耳机打一场架，用耳朵就能确认。**
> ⚠️ **本环境无 Unity、无 dotnet，以下全部条目均未验证，须由用户在本地逐条确认。**

### 9.1 听感验收（戴耳机，逐条可判）

| # | 怎么做 | 应该听到什么 |
|---|---|---|
| A-1 | 普攻砍中一个杂兵 | 先听到**一声破空**（挥击），紧接着**一声干脆的命中音**。命中音与 P1-2 的顿帧/闪白**在同一瞬间**发生，不脱节 |
| A-2 | 站着不动让敌人打你一下 | 声音**明显更闷、更低**，一耳朵就能和 A-1 的敌人受击音分开 |
| A-3 | 闭上眼睛，让队友随机操作 30 秒 | **光靠听就能说出"这下是我挨打 / 这下是我打人"**——这是 US-2 的核心验收，做不到就是没做到 |
| A-4 | 依次放技能1、技能2、闪避 | 三个声音**各不相同且可辨识**，不用看屏幕就知道放的是哪个 |
| A-5 | 打死一个杂兵 | 听到溃散音，**与命中音明显不同**，不会误以为只是又打中一下 |
| A-6 | 打 BOSS 到阶段切换 / 召唤 / 冲击波 | 三个事件的声音**互相可区分**，且冲击波音**足够醒目到让你想躲** |
| A-7 | 打死 BOSS | 明显是全场最重的一声，有情绪收束感 |
| A-8 | 打断敌人韧性（触发击退） | 一声脆裂的"咔"，**有奖励感** |
| A-9 | 安静站着听环境衬底 60 秒（R-10） | **听不出循环接缝**——没有周期性的"咔哒"或音量突跳。这是 R-10 的一票否决项 |

## 10. 边界与不做什么

| 不做 | 理由 |
|---|---|
| **旋律 BGM** | 见 §5。降 P2 且需主创拍板 |
| **引入任何音频文件** | §7.1 红线 |
| **动态混音 / 音频总线 / Audio Mixer 资产** | Mixer 是 `.mixer` 二进制资产，破坏 §7.1。三通道音量用纯代码乘法即可，本期量级不需要 Mixer |
| **3D 空间音效 / 混响区** | 俯视角 2D，收益低。距离衰减留 P2（R-18） |
| **语音 / 配音** | 无论如何都需要音频资源，直接出局 |
| **音频压缩 / 流式加载** | 程序化合成的短音效总内存在 MB 级，不需要 |
| **敌人技能音效** | 当前敌人不放技能（`Encounter.cs:759` 的 cast 路径只有玩家走）。留 P2（R-19） |
| **设置界面的音量滑条 UI** | R-06 只做**代码侧音量值 + 静音开关**。UI 归菜单模块，留 P2（R-17） |
| **音效编辑器 / 波形预览工具** | 调参靠 `AudioConfig` 改数字 + 重进 Play，够用了。不为此提前造工具 |
