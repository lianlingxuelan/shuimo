## 1. 产品目标

### 1.1 一句话说清「为什么现在打起来不爽」

**因为现在打中和没打中，屏幕上几乎长得一样。**

整局战斗里玩家能拿到的全部命中反馈，就是目标身上一次 `FlashDuration = 0.08f` 的整体染白（`CombatView.cs:82/207`）——80 毫秒，一次全身 Lerp 到白再退回，**没有停顿、没有镜头反应、没有数字**。于是三件事同时缺席：

- **打击不"实"**：攻击动作和伤害结算之间没有任何"咬合感"，挥空和打实的手感差异接近于零。
- **挨打不"疼"**：玩家自己被打时和敌人被打时用的是**同一套白闪**，玩家甚至不容易第一时间意识到"刚才掉血的是我"。在 `PlayerHpMax = 260` 的基准下，一次 20~40 的伤害只体现为血条悄悄短了一截。
- **输出不"可读"**：玩家完全不知道自己这一下打了多少。技能强弱、连招收益、精英/BOSS 的血厚程度，全靠猜。

本期要补的就是**从"命中判定发生了"到"玩家身体感觉到了"这一段**。它不增加任何玩法深度，但它决定 Demo 前 30 秒的第一印象。

### 1.2 这一版刻意不做什么

见 §5「边界与不做什么」。一句话：**只做"看得见"的四件事，不做"听得见"和"跑得快"的事。**

## 2. 用户故事

| # | 故事 |
|---|---|
| US-1 | 作为玩家，我希望**每次砍中敌人时画面有一瞬间的"咬住"感**，这样我才能分清"打实了"和"挥空了"，而不是全程像在划水。 |
| US-2 | 作为玩家，我希望**自己挨打时的反馈明显区别于敌人挨打**（颜色不同、震动更强），这样我不用盯血条就知道"刚才那下是我在挨揍"。 |
| US-3 | 作为玩家，我希望**看到自己每一下打了多少伤害**，这样我才能判断哪个技能值得放、这个怪还要几刀。 |
| US-4 | 作为玩家，我希望**重击和轻击的反馈强度不一样**，这样 BOSS 的大招砸下来时我能立刻感到"这下不对劲"，而不是和杂兵挠一下一个待遇。 |
| US-5 | 作为玩家，我希望**这些反馈不要糊住画面**——数字不遮住我的角色和技能栏，震屏不晃到我找不着人，节奏不因为反馈而变卡。 |

## 3. 需求池

优先级口径：**P0 = 缺了不能交付；P1 = 应该有，缺了体验打折；P2 = 有余力再做。**
下列所有数值均为**产品建议初值**，是给架构师和手感调试的起点，不是不可动的红线（唯一不可动的是 §6）。所有参数**必须外露为可调字段/常量**，便于现场试手感。

### 3.1 P0（必须有）

#### R-01　hitstop（命中顿帧）

| 项 | 建议值 |
|---|---|
| 触发条件 | 伤害**实际结算成功**时触发（即 `OnHit` 中 `applied == true` 的分支；被闸门拦下的命中**不得**触发） |
| 敌人挨打·轻击 | **0.05s** |
| 敌人挨打·重击 | **0.09s** |
| 玩家挨打 | **0.12s**（玩家自己挨打给最强顿帧，这是"疼"的主要来源） |
| 轻/重判定 | 单次伤害 ≥ 目标 `HpMax` 的 **8%** 记为重击（玩家侧即 ≥ 20.8 点伤害） |
| 并发去重 | 同一时刻多次命中**只取最长的一次**，不累加、不排队 |
| 冷却下限 | 两次 hitstop 起始间隔 **≥ 0.15s**，防止连击时画面持续卡顿 |
| 作用域 | **仅冻结表现层**（角色动画、特效播放、相机跟随）。战斗内核 `Scheduler.Tick(Time.deltaTime)`（`CombatController.cs:313`）**必须继续以真实 deltaTime 推进** |

> ⚠️ 实现方式由架构师定，但**不得用 `Time.timeScale`**。理由见 §6.1。

#### R-02　屏震（screen shake）

| 场景 | 幅度（世界单位） | 时长 | 说明 |
|---|---|---|---|
| 敌人挨打·轻击 | **0.05** | **0.08s** | 几乎是"点头"级别，只求有反应 |
| 敌人挨打·重击 | **0.12** | **0.14s** | |
| 玩家挨打 | **0.20** | **0.20s** | 玩家挨打是最需要被感知的事件 |
| 玩家被重击（≥15% HpMax，即 ≥39 点） | **0.30** | **0.26s** | 与 US-4 对应 |

- 抖动频率建议 **20~30 Hz**，幅度随时间**线性或指数衰减到 0**，结束时相机**必须精确回到无偏移位置**（不允许留下累计漂移）。
- 屏震是**叠加在 `CameraFollow` 结果之上的偏移量**，不得污染 `CameraFollow` 自身的 `SmoothDamp` 目标值与 `_velocity` 状态（`CameraFollow.cs:87`）。
- **边界安全**：抖动后的最终位置**仍须满足 `ClampToBounds` 约束**（`CameraFollow.cs:91/98`）。在地图边缘抖动时**绝不允许露出场景外的黑边**——这是本条的一票否决项。
- 并发去重：同 R-01，**取最强的一次**，不叠加。

#### R-03　受击闪白增强（区分玩家 / 敌人）

现状：`CombatView.PlayHitFlash()` 无参，玩家和敌人共用一套 `Color.white` + `0.08s`（`CombatView.cs:190/207/213`）。本期要让它**能表达"谁挨打"和"挨得重不重"**。

| 对象 | 闪色 | 峰值混合强度 | 时长 |
|---|---|---|---|
| 敌人挨打·轻击 | 纯白 `#FFFFFF` | 1.00（沿用现状） | **0.08s**（沿用现值，不改） |
| 敌人挨打·重击 | 纯白 `#FFFFFF` | 1.00 | **0.13s** |
| 玩家挨打 | **朱砂红 `#C0392B`** | **0.80** | **0.16s** |

- 玩家用红、敌人用白，是本条的核心：**一眼分清挨打的是谁**。红色取朱砂而非正红（`#FF0000`），是为了贴合水墨调性（见 §7 Q4）。
- 时长/颜色**必须参数化**，不能继续写死成 `private const float FlashDuration`。
- 重入行为：闪白期间再次被命中，**重置计时器为新的时长**（刷新，不叠加）。

#### R-04　伤害飘字（damage popup）

| 项 | 建议值 |
|---|---|
| 触发条件 | 伤害实际结算成功且 `dmg > 0` |
| 数值格式 | **整数**，`Mathf.RoundToInt(dmg)`（与 `CombatEventsUnity.cs:86` 现有写法保持一致）。**不显示小数**——内核是浮点，但玩家不需要看见 |
| 敌人受伤配色 | **墨黑 `#2B2B2B`** + **白色描边**（水墨基调，保证在深浅背景上都可读） |
| 玩家受伤配色 | **朱砂红 `#C0392B`** + 白色描边（与 R-03 玩家闪白同色系，形成统一语言） |
| 生成位置 | 目标当前位置**上方约 0.8 世界单位**，附加 **±0.25** 的水平随机抖动，避免连击时数字完全重叠 |
| 运动 | 向上飘 **0.6 世界单位** |
| 生命周期 | 总时长 **0.7s**：0~0.10s 缩放 0.8→1.15→1.0 弹入，0.10~0.45s 匀速上飘，0.45~0.70s 淡出至 alpha 0 |
| 重击强调 | 重击（判定同 R-01）字号 **×1.30** |
| 刷屏保护 | **同一目标 0.15s 内的多次伤害合并为一条，数值累加**（例如 0.1s 内挨了 8 和 12，只显示一条 "20"） |
| 同屏上限 | 同时存在的飘字 **≤ 12 条**；超出时**丢弃最旧的** |
| **HUD 避让** | 飘字**不得与底部技能栏重叠**。`HudSkillBar` 已占据 y ∈ [34, 110]（`BottomMargin = 34.0f` + `CellSize = 76.0f`，见 `HudSkillBar.cs:31/37`）。若飘字投影落入该区域，**必须上抬到 y > 120** |

#### R-05　暂停与结束时的正确收敛

- 当 `CombatBridge.IsGameplayBlocked == true`（`IsRunOver \|\| _menuPaused`）时：
  - **不得**新起任何 hitstop / 屏震 / 飘字；
  - 已在播的屏震**必须立刻归零并把相机放回无偏移位置**——在暂停菜单上抖屏是明确的 bug；
  - 已存在的飘字**冻结**（停止上飘与淡出计时），恢复后继续，或直接清除，二者取一但须一致。
- 玩家死亡 / RunOver 时，**所有残留飘字与震屏必须清理干净**，不允许飘字挂在结算界面上。
- 暂停状态的唯一入口仍是 `CombatBridge.SetMenuPaused()`，本期**不新增第二个闸门**。

## 4. 数量与基准参照

- 玩家血量基准 **`PlayerHpMax = 260`（平衡基准，永久钉死，本期不动）**。上文所有"占比"阈值均以此换算：
  - 8%（重击线）= **20.8** 点
  - 15%（玩家被重击线）= **39** 点
  - 30%（低血量线）= **78** 点
- 现有闪白基准 **0.08s**（`CombatView.cs:82`），本期**保留为"敌人轻击"档的原值**，以免整体反馈无谓变重。
- 相机跟随基准 `DefaultSmoothTime = 0.14f`（`CameraFollow.cs:28`）。屏震时长建议**不超过它的 2 倍**，否则抖动会和跟随平滑互相"打架"，看起来像镜头失控。

## 5. 边界与不做什么

**本期明确不做**，出现在实现里视为超范围：

| 不做 | 理由 |
|---|---|
| **音效** | `PlaySfx` hook 已存在（`CombatEventsUnity.cs:91`，已按 `Faction` 区分 `sfx_player_hurt` / `sfx_enemy_hit`），但**本期不接任何音频资源、不做 AudioSource 管理、不做音量控制**。留给独立的音频任务 |
| **粒子系统 / ShaderGraph / 后处理** | 不引入 `ParticleSystem`、不写受击溶解/描边 Shader、不加 Bloom 或径向模糊。闪白继续走 `SpriteRenderer.color` 的 Lerp 路子 |
| **对象池优化** | 飘字与特效沿用 `VfxSlash.cs` 的现有范式：**一次分配、播完自毁**。同屏 ≤12 条的量级不需要池化，**不要为此提前做架构** |
| **击退 / 受击硬直 / 无敌帧** | 这些会**改变战斗数值与推进节奏**，属于内核范畴，与 §6 硬约束直接冲突。本期一律不碰 |
| **处决慢动作 / 镜头拉近 / 命中定格特写** | 同上，且都绕不开时间缩放，风险高收益低 |
| **手柄震动（Rumble）** | 项目当前无手柄输入链路 |
| **设置面板里的"震屏强度/关闭反馈"选项 UI** | R-09 只做**代码侧系数**，不做设置界面。UI 归属菜单模块 |
| **暴击 / 元素属性 / 伤害类型分色** | 内核目前没有暴击与元素概念，飘字**不预留**这些分支，避免造出无人使用的抽象 |
| **伤害数字的累计统计 / DPS 面板** | 属于数据 HUD，不属于打击感 |

## 6. 硬约束（产品级，不可谈判）

### 6.1 受击反馈是**纯视觉层**，不得改变任何战斗数值与推进节奏

这是本 PRD 最重要的一条，优先级高于上面任何一个手感参数。**如果某个效果做不到"纯视觉"，那就不做这个效果。**

具体含义：

1. **禁止使用 `Time.timeScale`（含 `Time.fixedDeltaTime` 的联动修改）来实现 hitstop 或任何减速效果。**
   战斗内核在 `CombatController.cs:313` 吃的是 `Scheduler.Tick(Time.deltaTime)`。`Time.deltaTime` 受 `timeScale` 缩放，**一旦动 `timeScale`，内核会连同表现层一起被冻结/减速**，直接破坏确定性对拍。项目已有的 t1/t3 自检护栏与**倍率指纹 `2.5294x` 必须保持不变**。

2. **不得修改任何伤害数值、血量、冷却、技能参数、AI 决策时序。**
   反馈系统只能**读取**战斗事件，**不能写回**任何内核状态。

3. **不得改变内核的推进节奏。** hitstop 期间，内核照常按真实 `Time.deltaTime` 推进；被"冻住"的只能是渲染/动画/相机这类表现对象。**同一段输入序列，开反馈和关反馈跑出来的战斗结果必须逐位一致。**

4. **不得在内核脚本根（`Assets/Scripts/`）里引入新的表现层依赖。** 新增的反馈组件应落在 Unity 表现层（`Assets/_Project/Scripts/Runtime/`）。对 `Assets/Scripts/Systems/Combat/Unity/` 下既有文件（`CombatView` / `CombatEventsUnity`）的改动应**限于参数化与新增委托 hook**，不得引入新的逻辑分支影响事件语义。

> 具体技术方案（用独立累加器、表现层自己的 scaled time、动画 speed 归零，还是别的）**由架构师决定**。产品侧只钉死边界：**内核不许被碰。**

### 6.2 反馈不得与既有闸门冲突

暂停的唯一入口是 `CombatBridge.SetMenuPaused()`，`IsGameplayBlocked = IsRunOver || _menuPaused`。反馈系统必须**订阅并尊重**这个状态（见 R-05），**不得新增第二个暂停/冻结开关**。hitstop 的"冻结"与菜单暂停是两个概念，**不得复用同一个标志位**。

### 6.3 反馈不得遮挡既有 HUD

`HudSkillBar` 占据 y ∈ [34, 110]，这块区域**不允许被飘字或任何反馈元素覆盖**（见 R-04）。

## 7. 待确认问题

> 以下是我拿不准、需要在开工前拍板的事。**Q1 和 Q4 建议优先解决**——前者影响实现结构，后者影响整体调性，返工成本都不低。

**Q1（结构，需架构师确认）：受击闪白到底有几条链路在跑？**
我 grep 到 `PlayHitFlash()` 有**两个**调用点——`CombatEventsUnity.cs:81`（通用 `OnHit`，带 `applied` 闸门）和 `CombatEventsT3Unity.cs:148`（`OnSkillHit`）。需要确认：实际运行场景里这两条是**并存**（那么一次技能命中会不会闪两下、顿两次帧？）还是**只有一条被接线**？这决定反馈系统应该挂在**一个统一入口**上，还是要分别接两处并做去重。

**Q2（结构）：伤害飘字应该复用现成的 `PopupText` 委托，还是另起一套？**
`CombatEventsUnity.cs:49` 已定义 `Action<Vector2, string> PopupText` 并在 `:84` 调用，但**全仓无任何订阅方**，是个空挂钩。而技能链路 `CombatEventsT3Unity.OnSkillHit` **完全没有对应 hook**。如果复用，就需要给 T3 链路补一个同签名的委托；如果另起，则需要一个能同时覆盖两条链路的统一事件源。另外现签名只传 `Vector2 + string`，**没有"受击方是玩家还是敌人"的信息**，而 R-04 要求分阵营配色——签名要不要扩展？

**Q3（体验）：飘字用世界空间还是屏幕空间 Canvas？**
世界空间跟随角色更自然，但会随镜头缩放变糊、且难保证 R-04 的 HUD 避让；屏幕空间清晰可控，但需要每帧做世界→屏幕投影，且角色走出屏幕时行为要定义。我倾向**屏幕空间**（因为 HUD 避让是硬要求），但如果这与现有渲染管线冲突，请架构师直接推翻。

**Q4（调性，最需要主观拍板）：这套反馈的强度会不会盖过既有的水墨风格？**
这是我最没把握的一条。水墨的美学核心是**留白、克制、笔触的呼吸感**；而"打击感"这套东西（顿帧、抖屏、跳字、闪红）本质上是**动作游戏的重口味语言**，两者天然有张力。具体三个子问题：
- **(a)** 玩家受击闪**红**，是不是会在一屏水墨里显得很"塑料"？备选方案：不用红，而是用**浓墨压暗**（角色瞬间变深）来表达"挨打"，把红只留给飘字。哪个更对？
- **(b)** 伤害数字用什么字体？如果是常规无衬线数字，会不会和水墨背景严重违和？要不要走**书法/宋体数字**？但书法体的可读性（尤其是 3 位数快速跳动时）会下降——**可读性和调性哪个优先？**
- **(c)** 屏震幅度 0.20 会不会已经过头了？水墨画面里镜头一晃，笔触的静态美感很容易被破坏。是否应该整体把 §3 的建议值先按 **×0.7** 起调，宁可偏弱？
> 我的倾向：**先按建议值实现，同时把 R-09（全局强度系数）提到 P0 一起做**，这样可以在 0.6 / 0.8 / 1.0 三档之间当场 A/B，用眼睛而不是用会议来决定。但这需要主美/主创拍最终板。

**Q5（数值）：重击判定用"占目标 HpMax 的百分比"合适吗？**
好处是玩家和敌人共用一套口径；风险是**敌人血量差异大**——如果杂兵血很薄，那么几乎每一下都会被判成"重击"，分档就失效了。需要确认当前各类敌人的 `HpMax` 分布。如果差异过大，可能要改成**按伤害绝对值分档**，或**玩家侧和敌人侧用两套阈值**。

**Q6（范围）：击杀反馈（R-07）该放 P0 还是 P1？**
我放在了 P1。但从"打起来爽不爽"的角度看，**击杀瞬间恰恰是反馈收益最高的一刻**。如果实现成本很低（`EnemyDied` 是现成订阅点），建议提到 P0。请架构师评估后回话。

**Q7（性能）：同屏飘字 ≤12 条 + 不做对象池，在最坏情况（多敌人围攻 + 范围技能）下会不会掉帧？**
我按 `VfxSlash` 的"一次分配、播完自毁"范式定的规则，但没有实测依据（本环境无法运行）。如果实测有 GC 压力，请直接反馈，我调整同屏上限或把 R-13（配置化）换成池化。
