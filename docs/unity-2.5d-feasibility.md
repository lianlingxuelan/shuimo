# 2.5D 方向可行性评估

> 文档版本：v1.0 · 落盘日期：2026-08-09
> 作者：齐活林（Qi，交付总监）
> 工程路径：`F:/AI-project/ancientGame/shuimofeng/shuimofeng`（Unity 2022.3.62f3c1）
> 背景：用户提出将当前 2D 俯视角项目升级为 2.5D（3D 场景 + 2D 骨骼角色 + 八方向移动 + 重特效打击感），参考《斩妖行》水墨画风与《英雄联盟》3D 场景 + 2D 角色的表现方式。

---

## 1. 目标画面定义

| 维度 | 当前 2D 版本 | 目标 2.5D 版本 |
|---|---|---|
| 视角 | 正交俯视（Camera orthographic） | 等距/透视斜 45°（Camera perspective 或 ortho 倾斜） |
| 场景 | 程序化 2D Tilemap（32×32 tile） | 3D 场景（Terrain/Mesh + 水墨风格 Shader） |
| 角色 | 逐帧 PNG 精灵 + 代码驱动 SpriteRenderer | Spine/DragonBones 骨骼动画 + Billboard Sprite |
| 移动 | 八方向 WASD（已实现） | 八方向 WASD（**复用**） |
| 特效 | 2D 程序化数学（月牙剑气/光环/花瓣） | 3D 粒子系统 + 水墨 Shader |
| 相机 | 正交俯视阻尼跟随 | 等距透视 + 倾斜角度 |
| 战斗内核 | 纯 C# 内核（伤害/AI/BOSS/技能/状态） | **100% 复用** |
| UI | 代码生成 Canvas + Legacy Text | **80% 复用** |

## 2. 架构复用度分析

当前项目采用三层架构，对 2.5D 切换友好：

```
┌──────────────────────────────────────────────┐
│  表现层（场景/角色/特效/相机）                  │  ← 大改（~20% 复用）
├──────────────────────────────────────────────┤
│  Unity 薄壳层（CombatBridge/CombatEvents/View） │  ← 中等改动（~60% 复用）
├──────────────────────────────────────────────┤
│  内核层（Combat/Skill/Status/AI/Progression）   │  ← 100% 复用，一行不改
└──────────────────────────────────────────────┘
```

### 2.1 可原样复用的模块

| 模块 | 路径 | 文件数 | 复用率 | 说明 |
|---|---|---|---|---|
| 战斗内核 | `Assets/Scripts/Systems/Combat/` | ~20 个 .cs | 100% | 纯 C#，零 UnityEngine 引用，headless 可运行 |
| 技能系统 | `Assets/Scripts/Systems/Combat/Skills/` | 4 个 .cs | 100% | 技能定义/结算/意图全部逻辑层 |
| 状态系统 | `Assets/Scripts/Systems/Combat/Status/` | 4 个 .cs | 100% | DOT/属性修饰/叠层 |
| 伤害结算 | `DamageResolver.cs` / `WCore.cs` | 2 个 | 100% | 除法减伤/W-CORE 双层闸门 |
| 敌人 AI | `EnemyAI.cs` / `BossController.cs` | 2 个 | 100% | FSM 三态/BOSS 三阶段 |
| 成长系统 | `Progression.cs` | 1 个 | 100% | 经验/等级/属性曲线 |
| 数据文件 | `Assets/Data/zones.json` / `codex.json` | 2 个 | 100% | 6 个区域定义 |
| 确定性随机 | `PCG32.cs` | 1 个 | 100% | seed=20260730，fingerprint 不变 |

### 2.2 需要适配的模块

| 模块 | 复用率 | 改动量 | 说明 |
|---|---|---|---|
| 输入系统 | 90% | 小 | 多加方向映射，核心抽象不变 |
| 战斗桥接 | 60% | 中 | 装配流程需适应 3D 场景 |
| 战斗事件 | 50% | 中 | 特效钩子从 2D→3D 粒子 |
| 受击反馈 | 60% | 中 | 闪白/屏震/飘字基本复用，顿帧机制不变 |

### 2.3 需要重写的模块

| 模块 | 复用率 | 改动量 | 说明 |
|---|---|---|---|
| 世界生成 | 20% | **大** | Tilemap → 3D 地形（Terrain/Mesh） |
| 角色动画 | 30% | **大** | 帧动画 → Spine 骨骼，需引入 Spine Runtime |
| 角色渲染 | 30% | **大** | SpriteRenderer → Spine SkeletonAnimation + Billboard |
| 特效系统 | 40% | **中** | 2D 数学 → 3D 粒子 + 水墨 Shader |
| 相机系统 | 20% | **大** | 正交俯视 → 等距透视 |
| 敌人外观 | 10% | **中** | 彩色圆点 → Spine 精灵 |

## 3. 切换成本估算

### 3.1 时间估算

| 阶段 | 工作内容 | 估计轮次 | 说明 |
|---|---|---|---|
| P0 准备 | Spine Runtime 集成、基础 3D 场景搭建、相机配置 | 2-3 轮 | 环境就绪 |
| P1 核心 | 角色 Spine 动画 + Billboard + 八方向移动适配 | 2-3 轮 | 角色在 3D 场景中可动 |
| P2 战斗 | 战斗桥接适配 + 特效系统 + 打击反馈 | 2-3 轮 | 能打能受伤 |
| P3 完善 | 敌人外观 + UI 适配 + 调优 | 2-3 轮 | 完整可玩 |

**总计约 8-12 轮**（当前 2D 版本剩余约 0-1 轮即可交付 P0 全部）。

### 3.2 风险点

| 风险 | 等级 | 缓解 |
|---|---|---|
| Spine Runtime 与 Unity 2022.3 兼容性 | 低 | 官方支持，版本成熟 |
| 水墨风格 3D Shader 开发 | **中** | 可先用内置 Shader + 后处理滤镜占位，再做定制水墨 Shader |
| 骨骼动画手感不如逐帧 | 中 | 通过顿帧/屏震/特效补偿；可参考成功案例（空洞骑士 = 骨骼动画） |
| 3D 场景美术资产缺口 | **高** | 竹林/山石/流水 Model 需从零产出或购买 → 先用程序化几何体占位（Cube + 材质） |

## 4. 推荐路线图：三步走

### 第 1 步（当前）：2D 版本完成交付

- **状态**：P0 六项 + P1-6 成长 + P1-2 受击反馈已全部交付
- **剩余**：用户本地 Unity 验证收尾
- **产物**：一个完整的 2D 俯视角可玩切片

### 第 2 步：2.5D 技术验证（最小成本试错）

**目标**：用现有战斗内核，花 2-3 轮搭一个"竹林场景 + 一个 Spine 角色 + 砍竹子特效"的技术验证场景。

**验证清单**：
| 验证项 | 判定标准 |
|---|---|
| 3D 场景 + 2D 角色视觉融合 | 画面是否有《英雄联盟》式的景深感 |
| Spine 骨骼动画手感 | 移动/攻击/闪避动作是否流畅 |
| 打击反馈在 2.5D 下的表现 | 顿帧/屏震/飘字是否仍有"打到了"的感觉 |
| 3D 粒子特效 + 水墨方向 | 剑气/刀光在 3D 空间中的层次感 |

**核心原则**：验证失败可立即回退 2D 版本，内核零影响。验证通过则获得完整的 2.5D 技术方案。

### 第 3 步（验证通过后）：正式 2.5D 版本开发

- 基于验证结论，走标准 SOP：产品经理 PRD → 架构师设计 → 工程师实现 → QA 测试
- 内核层直接搬，不做任何改动

## 5. 关键决策待确认

| # | 决策项 | 选项 A | 选项 B |
|---|---|---|---|
| D-1 | 骨骼动画方案 | Spine（成熟，收费） | DragonBones（开源，功能弱） |

| D-5 | 是否保留 2D 版本 | 并存两版（维护成本高） | 只留 2.5D（切过去不回头） |

---

## 6. 结论

**不推荐现在切换。** 当前 2D 版本离完整可玩只差最后一口气（用户本地验证），先跑通再切，内核 100% 继承不浪费。

**推荐路径**：2D 版本完成 → 2.5D 技术验证（3 轮即可得出结论）→ 正式开发。

**保守估计**：如果验证通过、决策明确，从 2D 完整版到 2.5D 第一个可玩版本，约需 8-12 轮推进。
