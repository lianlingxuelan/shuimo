## 四个值得记住的发现

### 1. 已提交部分零冲突——冲突全在未提交的工作树里

```
git merge-tree --write-tree main feature/2.5d  →  退出码 0
```

这条命令直接决定了合并策略的形状：**冲突 100% 来自第 10 轮那约 5416 行未提交改动**。所以方案的第一步不是"解冲突"，而是"先把它落盘成 commit"——这批代码目前**没有任何 git 备份**，是全场唯一的单点风险。

### 2. CRLF 会伪造出"整文件冲突"

仓库 `core.autocrlf=true`：blob 是纯 LF，工作树是纯 CRLF。拿 `git show` 导出的文件直接和工作树文件做三方合并，会看到三个文件各报一个横跨全文的冲突块——**全是假的**。归一化行尾后立刻变干净。真实 `git merge` 不受影响，但手工比对时必踩。

### 3. 真冲突只有一处，且 `Bootstrap.cs` 是安全的

- `CombatBridge.cs` 唯一真冲突在 `-1366` 同锚点；原本担心的 `-343` 与 `-357` 间隔 9 行不重叠，git 自动合并。
- `Bootstrap.cs` 经核对为**严格超集**（`diff main→feat` 删除行数 = 0），自动合并出来的就是正确答案。
- ⚠️ 但**禁止用 `-X ours/theirs`**：误用会静默丢掉 `ResetStatics` + 幂等订阅，黑屏原样复发，而本环境的四项自证**全都发现不了**（纯 PlayMode 行为，只在第 2 次进 Play 时暴露）。

### 4. 变异测试抓到了 QA 自己写的护栏漏洞

这是本轮最有说服力的一幕。变异 M-B3（把"失败优先"改成"胜利优先"）**首轮没被捕获**。

根因很微妙：原用例自带 BOSS 债，有债时 `PendingAware = 0 + 1 = 1`，判胜分支的 `count <= 0` 条件本就不成立——**债自己把判胜分支挡死了**，所以对调 ④⑤ 优先级，结果照样是 Lost，用例依旧全绿。

结论：**判别性用例必须无债**。已拆成 `BP-B2a`（无债同归于尽，钉失败优先）/ `BP-B2b`（有债，验 I-2 不挡判负）后成功捕获。这是测试代码缺陷而非生产代码缺陷，QA 自行修复，未碰任何 C#。
